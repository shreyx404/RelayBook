🎯 1. The Problem & Solution

The Gap in Conventional Address Books

Ordinary address books store names and numbers, but they fail in two concrete, everyday ways:

🔴 Problem 1: Shared Staleness

A phone number and an email go stale at different speeds, but conventional records carry one shared "last verified" date — so users stop trusting the whole record when one field ages.

🔴 Problem 2: Emergency Neglect

The contact you need when things go wrong — a doctor, a hospital, an emergency relative — is held to the same standard as everyone else, and often has no fallback route at all.

RelayBook's Answer

RelayBook adds a small, explainable "reachability layer" on top of an address book:

  • Every route (phone, email, WhatsApp, Telegram, backup phone) is a first-class record with its own verification date.
  • A transparent rule-based advisor recommends which route to try next, quoting per-route ages: "Email was verified 20 days ago, phone 300 days ago: try email first."
  • Emergency contacts are held to stricter standards — 90-day recheck windows, 2 routes minimum, harsher scoring.
  • A structured "Is now a good time?" feature shows the contact's local time and whether their availability window is open.
💡

What RelayBook deliberately does NOT claim: The 0–100 score is a heuristic for route coverage and record freshness. It is not a probability that someone will answer. RelayBook does not send messages, verify ownership, or guarantee delivery.

⚡ 2. Feature Overview

📇 Contact Management

Add, list, edit, search, sort, and delete Person, Organization, and Emergency contacts. Full CRUD in both Swing and Browser UIs.

📡 Per-Route Verification

Save any number of routes (5 channels) with individual verification dates and labels. Each route ages independently.

🧭 Smart Route Advice

Get a suggested fallback route with a reason that quotes each route's own age. The advisor picks the freshest usable route automatically.

⏰ "Is Now a Good Time?"

See the contact's local time and whether their saved availability window is open right now. Supports weekdays, day lists, overnight windows.

✅ Quick Check-In

One-click "Mark checked today" — record-wide or per-route. No need to re-submit the whole form. Works in Swing and web.

📊 Directory Dashboard

Live stats: total contacts, stale count, single-route warnings, ready count, emergency contacts missing a second route.

📤 Export & Import

Privacy-aware vCard, CSV, JSON backup, and reachability summary. Import vCards with duplicate detection.

🔄 Live UI Sync

Create a contact in the browser → Swing table updates automatically. Observer pattern keeps both UIs in sync.

💾 Dual Storage

In-memory demo mode (zero setup) or MySQL persistence (transactional, normalized schema). No silent fallback.

🎨 4. OOP Design & Patterns

RelayBook implements four Gang-of-Four design patterns — each chosen because the domain genuinely needs it, not as a checkbox exercise.

🔶 Strategy Pattern — Routing Policies

Different contact types need different scoring strictness. Rather than if/else chains, the ReachabilityAdvisor delegates to a RoutingPolicy selected by type.

DefaultRoutingPolicy

Used for Person and Organization contacts. Standard freshness bands: ≤90d = 40pts, ≤180d = 30pts, ≤365d = 15pts.

1 route = 25 · 2 routes = 45 · 3+ = 60

StrictRoutingPolicy

Used for Emergency contacts. Harsher freshness: ≤180d = 15pts (vs 30), ≤365d = 5pts (vs 15). Below-minimum coverage = 10pts (vs 25).

Below minimum = 10 · Same band edges

// RoutingPolicy.java — Strategy interface with named constants
public interface RoutingPolicy {
    int COVERAGE_SINGLE_ROUTE = 25;
    int COVERAGE_TWO_ROUTES   = 45;
    int COVERAGE_THREE_PLUS   = 60;
    int STRICT_COVERAGE_SINGLE = 10;  // emergency below-minimum penalty

    int FRESH_WITHIN_90_DAYS  = 40;
    int FRESH_WITHIN_180_DAYS = 30;
    int FRESH_WITHIN_365_DAYS = 15;

    ReachabilityReport evaluate(Contact contact, LocalDate today);
}

// AbstractRoutingPolicy.java — shared skeleton, two hooks
public abstract class AbstractRoutingPolicy implements RoutingPolicy {
    public ReachabilityReport evaluate(Contact contact, LocalDate today) {
        // skeleton: pick routes, choose freshest fallback, explain...
        int score = Math.min(MAX_SCORE,
            coveragePoints(contact, routeCount) + freshnessPoints(days));
        // ...build full report with rationale, local time, window check
    }
    protected abstract int coveragePoints(Contact contact, int routeCount);
    protected abstract int freshnessPoints(long daysSinceVerified);
}

🟢 Observer Pattern — Live UI Sync

ContactService is the subject: it keeps a CopyOnWriteArrayList<ContactChangeListener> and notifies after every successful create/update/delete. The Swing frame is one observer; the reminder scheduler is another.

// ContactChangeListener.java — Observer interface with default methods
public interface ContactChangeListener {
    default void onCreated(Contact contact)  { }
    default void onUpdated(Contact contact)  { }
    default void onDeleted(Contact contact)  { }
    default void onReminderSweep(List<Contact> stale) { }
}

// AddressBookFrame registers itself:
service.addListener(new ContactChangeListener() {
    public void onCreated(Contact c) {
        SwingUtilities.invokeLater(() -> refreshTable());  // EDT discipline
    }
    // ...same for onUpdated, onDeleted
});

🟣 Template Method — Document Export

Document.export() is final: it calls appendHeader() → renderContent() → appendFooter(). Each document subclass (vCard, CSV, JSON, Reachability) fills the blanks.

public abstract class Document implements Exportable {
    public final String export() {   // ← cannot be overridden
        StringBuilder doc = new StringBuilder();
        appendHeader(doc);            // hook 1
        doc.append(renderContent());  // abstract — subclass fills this
        appendFooter(doc);            // hook 2
        return doc.toString();
    }
    public abstract String renderContent();
}

🟠 Builder Pattern — Contact Construction

The old 13-argument constructor chain is gone. Contact.Builder is fluent, validates in build(), and supports toBuilder() for immutable updates. Invalid contacts can never exist.

Contact emergency = Contact.builder(ContactType.EMERGENCY)
    .fullName("Dr. Mehta")
    .route(Channel.PHONE, "+91 98765 43210", LocalDate.now(), "Clinic")
    .route(Channel.EMAIL, "dr.mehta@hospital.in", LocalDate.now())
    .bestTime("Weekdays 10:00-17:00")
    .timeZone("Asia/Kolkata")
    .shareConsent(true)
    .build();   // ← validates: 2 routes ✓, name ✓, channels ✓

// Immutable update: copy → change → rebuild
Contact verified = emergency.toBuilder()
    .verifyAllRoutes(LocalDate.now())
    .build();

Key Value Objects

ContactMethod

Immutable value object. Holds a channel (PHONE, EMAIL, ALTERNATE_PHONE, WHATSAPP, TELEGRAM), a value, per-route last-verified date, and optional label.

withLastVerified(date) → new copy

TimeWindow

Immutable value object. Parses "Weekdays 18:00-21:00", "Mon,Wed 10:00-12:00", "22:00-02:00" (overnight), "any time". isOpenAt(ZonedDateTime) checks the contact's own time zone.

Result<T>

Generic either/or type: success(T) or failure(String). Used by the vCard importer so one broken card doesn't crash the whole file.

🧮 6. The Reachability Algorithm

The score is coverage + freshness, capped at 100. All point values are named constants in RoutingPolicy — no magic numbers anywhere in the logic.

Route Selection Logic

  1. Check the preferred route — if it's fresh (within the subtype's stale window), recommend it.
  2. If stale, scan alternatives — pick the route with the most recent verification date of its own.
  3. Build a rationale that names every route's age: "Phone was verified 300 days ago, email was verified 20 days ago: try email first."
  4. Missing dates are never invented — if there's no date, the advice says "has never been verified."

Staleness vs Score

They are separate concepts. Staleness comes from the contact subtype itself (person 180 days, org 365, emergency 90). A record is "stale" when its preferred route has no date or is past the window. The score is a combined coverage + freshness indicator — a contact can have a decent score but still be flagged "Needs verification."

Normalized v2 schema: each route is a separate row with its own verification date. Routes are unique per (contact, channel).

Key Database Properties

  • Transactional writes: A contact and its routes are always written in one transaction. Either everything commits or nothing does.
  • Cascade deletes: Deleting a contact removes its routes through ON DELETE CASCADE.
  • Prepared statements only: Every SQL parameter is bound, never concatenated.
  • Auto-migration: On first start against a v1 database (with flat phone/email/alternate_phone columns), the repository copies them into contact_methods inside a transaction, then drops the legacy columns.
  • No silent fallback: If DB_URL is set and MySQL fails, the app crashes with an actionable error — it never silently switches to in-memory.

Schema SQL

CREATE TABLE IF NOT EXISTS contacts (
    id                  VARCHAR(36)  NOT NULL PRIMARY KEY,

vCard Import

The VCardImporter processes cards one by one, producing a Result<Contact> for each. One broken card costs one rejected line, not the whole file. Duplicates (same name + shared route value) are skipped and reported.

⚠️

Privacy rule (load-bearing): Notes, relationship context, best time, and time zone never leave the app in any export. Route data needs shareConsent. Full backups must label themselves.

🔒 9. Security & Privacy

Same-Origin Guard

State-changing requests (POST, PUT, DELETE) are rejected with HTTP 403 when the Origin or Host header does not match the server's own host:port. This blocks two attack vectors:

🛡️ CSRF Protection

A malicious page on evil.example cannot POST to your local RelayBook — the Origin header would be http://evil.example, not http://127.0.0.1:8080.

🛡️ DNS Rebinding Protection

If an attacker rebinds their domain to 127.0.0.1, the Host header would still say evil.example:8080, not the server's own host.

Other Security Measures

  • Loopback binding by default: Binds to 127.0.0.1. Non-loopback HOST prints a clear warning.
  • Prepared statements only: No SQL injection surface.
  • Validation at construction: Invalid contacts cannot exist — the builder rejects them at build().
  • Honest limitations: No HTTPS, no authentication, no encryption-at-rest, no audit log. The app says exactly what it doesn't do.
// curl tests documented in README:

## Allowed (curl sends no Origin; Host matches):
curl -s -X POST http://127.0.0.1:8080/api/contacts \
  -d 'type=PERSON&fullName=Test&phone=%2B91+10000+00000'

## Rejected (cross-origin → 403):
curl -i -X POST http://127.0.0.1:8080/api/contacts \
  -H 'Origin: http://evil.example' -d 'type=PERSON&fullName=X&phone=1'

## Rejected (rebound hostname → 403):
curl -i -X DELETE http://127.0.0.1:8080/api/contacts/any-id \
  -H 'Host: evil.example:8080'

Class, Object, Constructor, this Contact(Builder) uses this.field = ...; ContactMethod, TimeWindow "The builder is the single construction path — one place where all fields are normalized."

static, final Contact.getCreatedObjectCount() (static counter), getId() is final, Document.export() is final, policy constants are static final "IDs cannot change, export skeletons cannot be overridden, and every policy reads from one constant pool."
Polymorphism getStaleAfterDays(), getMinimumRoutes(), describe(), getContactType() — dispatched through Contact references everywhere "The advisor never asks 'what type is this?' — it calls the method and the subtype answers."
Abstract class Contact, Document, AbstractRoutingPolicy "You can't instantiate a generic contact or a generic document — but you can process any concrete one through the base type."
Interface, multiple interfaces Exportable, Validatable, PrivacyLabelled, ShareableDocument, ContactRepository, RoutingPolicy, ContactChangeListener "ContactCardDocument extends Document AND implements ShareableDocument AND PrivacyLabelled — three contracts in one class."
